# D16 · 并查集

> 4 个单元，每个单元三段：**学术**（定义/不变量/为什么对）→ **实操**（仓颉写法/边界/实测）→ **建议**（做完对应题目再看）。
> 本关只讲一件事：**用代表元维护等价类**。`fa` 数组、路径压缩、按大小合并解决了"动态连通性"；Kruskal 只是把它接到"排序后的边"上。

## 16.1 并查集基本操作（D16-A）

### 学术

- 并查集维护的是顶点集上的**等价类划分**：每个类选一个**代表元**（根），`find(x)` 返回 x 所在类的代表元
- 不变量：`fa[r] == r` 当且仅当 r 是根；其余点沿 `fa` 一路上溯必然到达根（无环，因为只在合并时改一次父亲）
- `union(u, v)` 就是把两个类合成一个：把一棵树的根挂到另一棵树的根下；`u`、`v` 连通 ⇔ `find(u) == find(v)`
- 复杂度：带路径压缩（并按大小合并）时 m 次操作总代价 O(m·α(n))，α 是反阿克曼函数，实际 ≤ 4

### 实操（仓颉）

- 数组开 `Array<Int64>(n + 1, repeat: 0)`，初始化 `fa[i] = i`；用 1 基下标，省掉 0 号位的边界判断
- `find` 用**两趟循环**：第一趟走到根，第二趟从原结点重新走并边走边改写 `fa[当前] = 根`
- `unite` 返回 `Bool`（是否真的合并了两个不同类），后面做 Kruskal 判环时直接用它
- 读入 `op u v` 后按 `op` 分派：`1` 合并、`2` 查询；输出用 `StringBuilder` 累积再一次 `print`
- 实测：D16-A 的 05 用例（n = m = 1000）在 judge 里约 53 ms

### 建议（做完 D16-A 之后看）

- 连通性判断一定写 `find(u) == find(v)`，**不要**写 `fa[u] == fa[v]`（只有根的父亲指向自己，普通结点的父亲随时会被压缩改写）
- 自检三件事：`u == v`（自合并/自查询）、同一对重复合并、先查询后合并（必须先 `NO` 后 `YES`）
- 别用递归写 `find`：链长时深度上千，显式循环既安全又快

## 16.2 朋友圈计数（D16-B）

### 学术

- 全部合并做完后，**块数 = 根数** = `{ i : fa[i] == i }` 的元素个数；这一步只需 O(n) 扫一遍
- 块规模不能事后数：要在合并时把 `sz[小根]` 累加到 `sz[大根]` 上，只有根上的 `sz` 有意义
- 统计是"离线一次结算"：所有 `unite` 结束后再数根，不要在每个关系到来时都统计一遍（那是 O(nm)）
- 复杂度 O((n + m)·α(n))；n、m 都到 2×10⁵ 时可以在 1 秒内完成

### 实操（仓颉）

- 两个平行数组 `fa` 与 `sz`（`sz` 初值全 1）；按大小合并时把小的挂到大的下面，同时 `sz[新根] += sz[旧根]`
- 统计循环里用 `fa[i] == i` 判根、用 `sz[i]` 取人数，都只在根上取值
- `m = 0` 也要正确处理：此时没有任何输入行，直接进统计，`groups = n`、`largest = 1`
- 实测：D16-B 的 05 用例（n = m = 2×10⁵）在 judge 里约 473 ms

### 建议（做完 D16-B 之后看）

- 只输出 `groups` 与 `largest` 两个数，**不要**输出根编号——根是谁取决于合并顺序，判题会直接判错
- 自检：全是孤立点（m = 0）、全连成一片（m = n-1 的链）、以及重复给出的同一对关系
- 如果题目改成"输出每个块的大小并排序"，记得收集 `sz[根]` 之后要排序（并查集内部顺序没有意义）

## 16.3 压缩与按秩（D16-C）

### 学术

- 只写 `while (fa[x] != x) { x = fa[x] }` 的 `find` 最坏 O(n)：数据按 `1-2, 2-3, …` 铺成一条长链时，单次查询就要走 n 步
- 路径压缩把"链"变成"星"：第一次 `find` 是 O(链长)，之后同一个点的查询变成 O(1)；均摊到每次操作是 O(α(n))
- 按大小/按秩合并是第二道保险：即使不做压缩，树高也被限制在 O(log n)
- 一关的判据是"m 次操作的总代价"：压缩前 O(nm)，压缩后 O(m·α(n))，n = 2×10⁵ 时差距是 10¹⁰ 与 10⁶ 量级

### 实操（仓颉）

- 压缩必须**两趟**：先往上找到根 `r`，再从原结点 `x` 重新走一遍，途中 `fa[每个点] = r`
- `unite` 里两次 `find` 都要走同一个压缩版 `find`，别只压缩一半
- 输入输出量都大（m = 2×10⁵ 行），逐行 `println` 会拖慢；用 `StringBuilder` 攒起来
- 实测：参考实现跑 D16-C 的 05 用例约 471 ms；把 `find` 换成"不压缩 + 不按秩"后同一份数据 **>15 s 超时**

### 建议（做完 D16-C 之后看）

- 自测动作：造 `1-2, 2-3, …, (n-1)-n` 再反复查 `1` 和 `n`——这是并查集最经典的卡常数构造
- 想确认自己写的是真压缩：在 `find` 末尾打印一趟走过的长度，第二次查询同一对点时它应该变成 1
- 按大小合并和路径压缩可以只写一个（都能过），但两个都写才是标准写法

## 16.4 Kruskal 最小生成树（D16-D）

### 学术

- **割性质**：对任意把顶点集分成两半的割，横跨该割的最小权边一定属于**某**棵最小生成树。所以"全局按边权升序、能用就用"不会错过最优解
- 正确性：Kruskal 选边时若一条边连接两个不同连通块（不成环），就把它并入；归纳可证已选边集始终是某棵 MST 的子集
- 终止条件：选够 `n-1` 条边即得 MST；遍历完所有边仍不足 `n-1` 条 ⇔ 图不连通
- 总代价 O(m log m)（排序主导）+ O(m·α(n))（判环）；总权重最大 n·w = 10⁵ × 10⁹ = 10¹⁴

### 实操（仓颉）

- 边存成元组 `(w, u, v)` 放进 `ArrayList`，`sort(edges, by: {...})` 按第一维升序；权相同时选谁都一样
- 逐条扫边：`if (dsu.unite(u, v)) { total += w; used += 1 }`，`used == n - 1` 时提前 `break`
- 自环（`u == v`）和重边不需要特判，`unite` 自己会返回 `false`
- 累加用 `Int64`；`println("mst=${total}")` 之前不要经过任何 32 位类型
- 实测：D16-D 的 05 用例（n = 10⁵、m = 2×10⁵）在 judge 里约 745 ms；04 用例总权重 9.99×10¹¹，明确超出 32 位

### 建议（做完 D16-D 之后看）

- 自检三件事：n = 1 且 m = 0（输出 `mst=0`）、图不连通（输出 `IMPOSSIBLE`）、以及权 0 的边（必须被选中，不能当"没边"跳过）
- 判"选够 n-1 条"用计数器，不要用 `used == n - 1` 之外的条件（比如"遍历完所有边"）
- 想更快可以改用 Prim + 堆，但边权稀疏图里 Kruskal 的排序往往是常数最小的一档
