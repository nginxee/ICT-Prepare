# D4 · 队列与双端队列

> 4 个单元，每个单元三段：**学术**（定义/不变量/为什么对）→ **实操**（仓颉写法/边界/实测）→ **建议**（做完对应题目再看）。
> 本关的统一主题是 FIFO 的代价藏在"从哪一头取"：数组尾插尾删都是 O(1)，头删是 O(n)，所以队列必须自己管两个指针。

## 4.1 队列模拟（D4-A）

### 学术

- 定义：队列是只允许队尾插入、队首删除的线性表（FIFO）；用环形缓冲实现时"逻辑位置"与"物理下标"靠取模换算
- 不变量：`cnt` 恒等于逻辑元素个数；`head` 指向队首、`tail` 指向队尾的后一格；`cnt > 0` 时 `buf[head]` 就是队首
- 为什么对：出队只挪 `head`、入队只写 `buf[tail]` 再挪 `tail`，两者都对 cap 取模，缓冲区被循环复用，任意时刻 `cnt ≤ cap`
- 代价：每条指令 Θ(1)，总 Θ(m)；判空判满的判据是 `cnt`，不是 `head == tail`（二义性见 4.2）

### 实操（仓颉）

- 标准库没有 `Queue`：`Array<Int64>(m, repeat: 0)` 加 `head` / `tail` / `cnt` 三个 `Int64`
- 读指令：`readln().getOrThrow().trimAscii().split(" ")`；`PUSH` 的第二个片段才是数
- `ArrayList` 的 `remove(at: 0)` 是 O(n)：05 用例先灌 10⁵ 个元素再连续出队，头删累计搬约 5×10⁹ 次元素，必然超时
- 输出用 `StringBuilder` 拼一次 `print`；10⁵ 行逐个 `println` 明显更慢
- 实测：m = 2×10⁵ 的 05 用例在 judge 里约 350 ms

### 建议（做完 D4-A 之后看）

- 只要"两头进出"，就先想手写环形缓冲；容量上界已知（本题等于 m）时直接开定长数组，不必动态扩容
- 判空一律看 `cnt`；把 `head == tail` 当作空判据，会在"刚好满"时误判
- 自检动作：把 05 用例的解法临时换成 `ArrayList.remove(at: 0)` 跑一次，亲眼看到超时

## 4.2 循环队列（D4-B）

### 学术

- 定容队列 = 容量约束下的 FIFO；容量固定意味着"满"是一种显式失败，而不是自动扩容
- 二义性：`head == tail` 既是空也是满（两个指针重合），所以判空 / 判满必须引入第三份信息（计数或留一格空）
- 不变量：`0 ≤ cnt ≤ cap` 且 `tail = (head + cnt) % cap`；这条式子既能校验状态，也能定位第 i 个元素
- 代价：每操作 Θ(1)，收尾打印 Θ(cap)

### 实操（仓颉）

- 直接加一个 `cnt` 字段最省事：入队前 `if (cnt == cap)`，出队前 `if (cnt == 0)`
- 打印剩余元素要从 `head` 起走 `cnt` 步、每步 `(p + 1) % cap`，不能从下标 0 顺扫
- `cap = 1` 是最有效的边界：`head` / `tail` 永远落在 0，取模写错立刻暴露
- 实测：cap = 10⁵、m = 2×10⁵ 的 05 用例约 346 ms

### 建议（做完 D4-B 之后看）

- 真实系统里"满了就报错"比"自动扩容"更常见（缓冲区、环形日志、串口）；先想清楚满了是丢新的还是丢旧的
- 除非题面要求，别用"开 cap+1 个格子、留一格空"的判满技巧：它省一个变量，却把 `tail` 的语义变复杂
- 自检动作：构造"填满 → 全部出队 → 再填满"，第三轮 `head` 已绕过数组末尾，取模写错必现

## 4.3 约瑟夫环（D4-C）

### 学术

- 定义：n 个元素围成环，每次跳过 k-1 个、删除第 k 个，重复到空
- 等价变换：环上的"跳过"正好是队列旋转 k-1 次（弹队首再塞到队尾），旋转后队首就是被删除者
- 正确性：旋转不改变元素多重集与相对次序，只改变"谁是队首"，因此每轮删除的正是原环上第 k 个
- 代价：Θ(n·k)；k 与 n 同阶时这类模拟不可行（需要名次树，本大纲不覆盖）

### 实操（仓颉）

- 队列容量取 n 就够：每轮"弹出 + 塞回"个数相同，元素总数守恒
- 旋转写法：`buf[tail] = buf[head]; head = (head+1) % cap; tail = (tail+1) % cap`
- `k-1` 次旋转用 `while` 循环，不要递归；k = 1 时循环 0 次，正好每轮删掉队首
- 实测：n = 2×10⁵、k = 10 的 05 用例约 291 ms（约 2×10⁶ 次进出队）

### 建议（做完 D4-C 之后看）

- 只在 k 很小的时候用队列模拟；k 与 n 同量级要立刻换思路
- 别用 `ArrayList.remove(at: pos)` 删中间元素：单次 O(n)，整体 O(n²)
- 自检动作：n=7、k=3 应得 `3 6 2 7 5 1 4`；n=16、k=2 应得"先把偶数全删完，再删奇数"

## 4.4 滑动窗口最大值（D4-D）

### 学术

- 朴素做法对每个长度 k 的窗口扫一遍，Θ(n·k)；k 到 10⁵ 时约 10¹⁰ 次比较
- 单调队列不变量：队列存**下标**，对应的值自队首向队尾单调递减，因此队首恒为当前窗口最大值
- 为什么对：新元素入队前弹掉所有 `≤ a[i]` 的尾部元素——它们既更老又不更大，永远不可能再当窗口最大值；队首滑出窗口即弹出
- 代价：每个下标最多进队一次、出队一次，总 Θ(n)，额外空间 Θ(k)

### 实操（仓颉）

- 双端队列用 `Array<Int64>(n, repeat: 0)` 存下标 + `h` / `tl` 两个指针，区间 `[h, tl)`，两端都是 O(1)
- 右端弹出必须带等号：`while (tl > h && a[dq[tl-1]] <= a[i]) { tl -= 1 }`；写成 `<` 时重复值堆积、效率退化
- 左端弹出：`while (dq[h] <= i - k) { h += 1 }`，是 `i-k` 而不是 `i-k-1`
- 窗口未满（`i < k-1`）时不输出；结果是 n-k+1 个数
- 实测：n = 2×10⁵、k = 10⁵ 的 05 用例约 234 ms

### 建议（做完 D4-D 之后看）

- 判据："每个窗口的极值 / 第一个满足条件的元素"→ 单调队列；"窗口和 / 计数"→ 前缀和或滑窗
- 队列里必须存下标：只有下标才能判断"是否已经滑出窗口"
- 自检动作：用全部相同的值跑一遍，输出应有 n-k+1 个且全相同；若变慢或长度不对，就是等号或 `i-k` 写错
